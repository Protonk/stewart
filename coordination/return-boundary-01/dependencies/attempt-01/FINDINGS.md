# What a finite return could let end

Dependency challenge, 2026-10-26. Documentary findings and recommendations, not
an adopted Promise/Yield interface, product change or authority to withdraw an
obligation. The complete source/read account is in `SOURCE-LEDGER.json`; exact
displayed excerpts and commands are retained under
`.scratch/return-boundary-01/dependencies/r01.txt` through `r26.txt`.

## Finding and acceptance rule

A finite return can replace access to the auditor's former environment **for a
specified recipient task** if it carries, or binds to independently available
material carrying, the question, attributed argument, inspectable support and
qualifications that task needs. That is a hypothesis for the recipient study.
It does not establish durable retrieval, truthful reported execution, safe
termination or permission to discard anything. Fewer fields do not discharge
more undertakings. An omitted purpose needs an explicit relinquishment decision
and its consequences stated beside it.

The reduction claim therefore needs five terms: the connection proposed to end;
the exact purpose served; the retained material or expressly relinquished
purpose; who undertakes to make the replacement available for how long; and an
observation that would show the replacement insufficient. A reduction is not
demonstrated by counting files, fields, commands or source lines alone.

The selected falsifiers challenge the replacement's stated claim; they do not
require a preferred substantive answer. A contradiction, an honest evidence
limit or a proposed reframe can be faithfully carried by a successful return.

The study's return-only phase is a **diagnostic restriction**, not a proposal to
deny managers their own pinned subject source. It helps distinguish what the
return says from what a recipient reconstructs elsewhere. A later finite source
grant can establish that a stable, independently available subject revision
serves a need without retaining the auditor's private workspace. It does not
imply that every answer must contain all source code.

## Classify a dependency before claiming to end it

| Connection class | Proper treatment in this inquiry |
| --- | --- |
| Manager-owned pinned subject and original question | May remain intentionally available independently of the audit. Record exact revision/member and actual availability; a hash naming unavailable bytes is insufficient. Restoration of this class is not by itself evidence that the retired auditor environment was needed. |
| Auditor-authored reasoning, specimens, notes or observations | Decide which finite selections belong in the return or stable support. If a recipient needs omitted original support, reconstructing an equivalent argument from subject source does not establish that the auditor's argument was preserved. |
| Auditor's mutable working environment and private scratch | This is the live dependency the candidate principally seeks to end. Ending it requires a supported replacement for every surviving preservation undertaking, or a prospective authorized change of promise. A source-code need should not automatically be classified as a private-scratch need. |
| Custody records, writer, location and delivery endpoint | A reader's useful understanding of text is not evidence that a package can be verified, retrieved after cleanup, delivered or resumed after a lost reply. These are separate operational dependencies. |
| Launch/control, other live uses and held material | An answer can end investigative work without proving execution ended or releasing custody. Actual stop, safe removal scope, holds and unfinished operations require independent evidence and authority. |

## What this wave can and cannot settle

This wave can find **specific missing or preserved dependencies** in A1/A3
packet readings: whether the return expresses a claim, whether its qualifications
travel with it, which support can be inspected, what remains attributed, and
what a precisely staged restoration changes. It can defeat a claim that a
particular packet already serves a particular recipient task. An unchanged
substantive conclusion does not show that support survived; a changed conclusion
does not by itself show a defective representation.

It cannot establish a general answer schema, fresh constrained authoring,
enforced read restrictions, durable storage, actual historical execution,
delivery, safe stop, retirement, recovery or normal auditor-route usability.
It also cannot decide which protected purposes should be relinquished. C
123–131 and V 90–110 prohibit using agreement or schema validity as substitutes.

The prior pilot is relevant for method, not an answer key: all four first
recipients used source; one reconstructed omitted reasoning (P 12–24, 70–97).
The integration review confirms the report's narrower distinction and rejects
causal format or time-cost inferences (IR 13–27). No prior recipient response,
A1/A3 case source, held-out review or current producer result was read here.

## Decision gate

Carry forward a candidate only with a named task, support/qualification map and
recorded failures. An observed need for one finite original support unit argues
for that unit or an explicit capability limit, not automatically for arbitrary
attachments or permanent live access. An observed need for manager-owned source
may justify a stable reference. A need for disposable private work contradicts
the claimed replacement unless the purpose is expressly relinquished. None of
these observations alone authorizes changing M5–M10 or M13–M14 obligations.

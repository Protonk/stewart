# A1 finite-return specimen design

Status: provisional content specimens, 2026-10-26. No product schema adopted.
The question is whether the identity and scope of removable resources survive
session/registry observations, CLOSING.json and actual deletion, including retry.
The recipient needs the original question and its Information preservation recipe.

## What connection could end, and for what purpose

The finite return can replace browsing the auditor's report and prose notes when
the recipient's purpose is to examine **what the auditor says, its stated basis,
qualifications, and proposed discriminating checks**. That undertaking requires
more than the answer paragraph: the trace, scenarios, bounds, countercases and
unresolved premises carry distinctions that the answer alone cannot preserve.
The original return is itself finite: 33,698 source bytes across one report and
two notes. The candidate adds navigational organization; it is deliberately not
a compression claim.

The return does not replace independent inspection of the cited implementation,
test fixtures, deployed Git/interpreter or actual filesystem behavior. A line
citation gives an identified lead, not the cited bytes or proof those bytes were
used. The historical report is static and explicitly says no project code,
tests or scenarios ran. A recipient who requires execution evidence has reached
an admitted ceiling, not discovered a missing execution attachment.

| Connection | Recipient purpose | Bounded replacement or remaining dependency |
| --- | --- | --- |
| Original report file | Inspect the attributed answer and its scope | Verbatim report blocks, original identity, question and recipe |
| Auditor's notes directory | Inspect preliminary observations and candidate reasoning | Both notes verbatim, separately attributed; final/preliminary status preserved |
| Repository browsing | Check whether cited code/test behavior is represented accurately | Not replaced by the report. Optional exact selected source excerpts are supplied separately as a new context selection |
| Live audit environment | Inspect versions, actual access, execution or stopping | Not replaced; the return disclaims measurement and cannot demonstrate these properties |
| Original custody records | Establish collection/receipt and delivery authenticity | Manifest identities remain supplied metadata; the finite text does not recreate the receipt chain |

## Packet construction and substantive coverage

`01-original/PACKET.md` encloses the unchanged report and both unchanged notes in
separately attributed text blocks. Its directory also contains three byte-exact
individual files. `02-finite/PACKET.md` supplies the same source population in 23
source-heading blocks, with an editorial navigation list specific to this
question: identity/coverage, resource trace, claimed changes and boundaries,
preconditions/unknowns, next checks, and preliminary trail. It preserves source
order and every source byte, including repeated statements. The full return was
already usefully organized, so a more aggressive reorganization or contraction
would add editorial judgment without being needed to test ended access.

Editorial prose is explicitly labelled. Historical assertions are fenced;
whole-source Git identities and SHA256 values identify their provenance. These
identities are not additional historical auditor assertions. The original
`audit-report` declaration remains quoted evidence, not a new completion claim.
Nothing converts claims into a required positive/negative finding or certifies
support. An uncertain answer or disagreement remains expressible.

`INVENTORY.json` partitions all 33,698 original report/note bytes into 68 paragraph
blocks and records the disposition of each. All are retained in the baseline and
candidate. Repetition is retained because early notes can disclose development
of a claim, different confidence, a distinction, or an unresolved premise. No
asserted equivalence between preliminary notes and final report is silently
substituted for their wording. The prompt is copied unchanged as shared context;
the recipe is an exact selected section with source offsets in its own map.
Roles were read as production context; they are not silently added to recipients'
question/recipe supply.

## Field pressure exposed by this question

The following are content obligations for this specimen, not proposed schema keys.

- A resource's **recorded operand** and its **referent or lifetime identity** must
  remain distinct. The report's first finding concerns attribution on retry,
  not an asserted widening of deletion. Collapsing these would change the answer.
- The resource-class trace needs producer, inventory construction, retry read,
  actual deletion consumer and stated consequence. A path list without the
  consumer's use cannot carry the information-preservation argument.
- The ordinary-operations variant and the remnant variant have different
  premises. U2 applies to the remnant variant; the report does not establish
  either variant by execution. Removing that qualification would promote it.
- Finding 2's gates and required writer scope cannot be detached from its
  scenario. The report distinguishes hostile auditor contents from a checkout
  parent changed by another writer. Calling both simply hostile checkout data
  would alter the undertaking.
- The no-supported-broadening account for static in-worktree contents, claim
  boundaries A/B/C/E/L, trust assumptions T1–T4, concurrency, and U1–U4 stay
  visible alongside findings. They are not expendable negative space.
- Written test assertions, Git/interpreter premises, unexecuted predictions,
  helper-reported byte matches and harness-setting uncertainty keep their
  attribution. Source fidelity does not turn any of these into measurement.
- Proposed contrasts identify the control, changed property, invariance arm,
  predicted operands/outcomes and competing explanations. They remain proposed
  work requiring another grant, not a continuation entitlement.
- Preliminary observations, claimed coverage, inherited context and stopping
  reason remain available. A recipient can contest the stated account without
  needing a new success vocabulary or agreeing with the auditor.

## Matched diagnostic omission

`03-finite-omission/PACKET.md` differs from the finite candidate by exactly one
404-byte contiguous deletion: the **Tests** paragraph inside Finding 1. It says
the existing guard is exercised by moved-checkout controls, that the interrupted
close test interrupts before Git frees the admin name and inserts no prepare,
and that the second-audit invariance test has no interruption. This is one
bounded argument about why existing tests do not distinguish the reported retry
failure. All claims, neighboring qualifications, scenarios and other support
remain intact. It is not a recommended return boundary.

This paragraph has no numbered members, and its removal leaves the next
Finding 2 heading after the preceding First-close reach paragraph. There is no
cut marker, altered enumeration, dangling reference or new summary. The two
packets have exactly the same editorial text. Their filenames and external maps
identify the experimental condition; the coordinator should supply neutral
recipient paths and withhold the design/maps to avoid an easy condition cue.
The 404-byte reduction and absence of a Tests subsection are inherent cues, not
independently eliminated by this design.

Neither note repeats that test-coverage argument. Residual corroboration is
intentionally retained: note 2 candidate F and the report's answer/scenario cite
`test_repository.py:269-283` as a Git-name-reuse assertion. Note 1 records the
unverified name-reuse concern. The report keeps the full mechanism, proposed
reuse control and invariance arm, and its general warning that tests were not
run. Those may let a recipient independently notice a coverage question; their
presence means the omission might have little effect. A null difference would
not show the omitted argument universally unnecessary. No extra material was
removed to force sensitivity.

## Restoration that separates missing support from new investigation

1. Ask recipients to inspect the stated distinction, strongest support, relevant
   limits and smallest further evidence needed, without requiring the historical
   conclusion. In particular, they may say the return is enough to understand
   the proposed retry failure but not to verify it.
2. Restore `RESTORE-TEST-COVERAGE.md` with its explicit report attribution. It is
   exactly the omitted paragraph. Improvement specifically in identifying the
   limitations of current tests would support a missing-stated-support account.
   A generic request for source before and after restoration would not.
3. If the unresolved purpose is verifying those test assertions, optionally
   provide `proposed-context/TEST-COVERAGE-SOURCE.md`. Its four exact test excerpts
   are newly selected from captured target source, not historical auditor output.
   These can permit source inspection of the stated contrasts; missing fixture
   details must remain a stated limit.
4. `proposed-context/RETRY-REGISTRATION-SOURCE.md` is a separate possible source
   restoration for the registration mechanism and name-reuse assertion. Opening
   it changes the recipient's evidentiary basis from report examination to a
   bounded independent code reading. It still supplies no execution results and
   no permission to run the historical code or resume its audit.

No finite specimen guarantees that every future challenge is answerable. A
recipient can identify an essential omitted dependency; the response is either
another finite selected undertaking or explicit relinquishment of that use.
The whole-return boundary remains insufficient for independent runtime behavior,
full implementation completeness, deployment assumptions, actual harness
constraints, receipt-chain authenticity, stopping, retirement and recovery.
This content study establishes none of those facilities.

## Evidence and controls

`BLOCKS.json` carries source order, exact content, source offsets, lengths and
hashes for all 23 blocks. `PACKET-MAPS.json` records ordered source and editorial
segments for every packet, enabling byte-exact reconstruction and a future
content-identical reorder control. `INVENTORY.json` accounts for every original
paragraph. `OMISSION.json` records the sole removed span, outside recipient
packets. `READS.json` records actual file identities and whether the model saw
whole text or selected lines. Source originals and the full baseline remain
independent witnesses outside the omission treatment through review.

The static checker verifies all source identities, source-byte coverage,
reconstruction, unchanged original files, single contiguous omission, original
witness, restoration identity and selected code-excerpt identity. Its results
concern artifact fidelity only. They do not establish intellectual sufficiency,
recipient comprehension, enforcement, historical execution or successful return
retrieval by Stewart.

## Added order control and shared-context decision

At the coordinator's request, `04-finite-order/PACKET.md` exchanges the two
complete attributed note groups after the unchanged report. Its editorial
introduction, report, all 23 source units, attribution wrappers and length are
identical to the full candidate; only unit order differs. `REORDER.json` records
the permutation and inverse. Unit-multiset equality and inverse restoration
pass. This is a deliberately limited order manipulation: it tests the placement
of preliminary notes, not robustness to rearranging the central argument.
`PACKET-MAPS-02.json` extends the initial map without changing any first-three
packet identity or the initial map.

The coordinator explicitly chose to supply original historical role files as
common context with prompt/recipe across arms. That is an equal disclosed
addition, not an inference that the historical auditor read the maintainer role.
The historical report's own not-opened list stays unchanged.

# Helper materialization: consumers and next qualification

Source-only finding at `250d494262374007302ea9765399cb27dce90a34`. No new recovery population or executed comparison is claimed.

The two documented consumers are real **source-documented uses**, not observed user demand: inspecting retained pristine helper bytes, and explicitly choosing those bytes as the manager source for a separately authorized fresh assignment. `src/stewart/runtime.py:287–351` and bundled `src/stewart/resources/README.md:1314–1327` state both. Recovery preserves a source session digest/assets binding, records materialization and capture failures, and never retargets old commands/scopes/releases. New work in that directory is precisely why the decided close rule compares it to its own capture and treats drift as unjudged.

`RETURN-CUSTODY-DESIGN.md:217–235` proposes a bounded captured-asset reader for inspection and explicit export for fresh reuse. That proposal serves the named uses in principle, but the final route is not just an already-proven composition:

- `handoff.py:206–241` selects the complete `runtime-assets` manifest/archive pair and writes selected payloads under package members. The bundled manual `:1556–1581` describes numeric payload names and a manifest mapping. This is a custody package, not a recovered executable source-root layout.
- `captured.py:226–263` verifies assets and can return per-path bytes. Reading/importing an evidence package verifies the selected group; it does not authorize execution or select a manager source.
- `tests/test_stewart_runtime_export.py` covers exported groups and corrupt/partial substitutions; `tests/test_runtime_recovery.py` covers the existing materialization mechanism. Their existence does not demonstrate the proposed export-to-fresh-source replacement. No tests were run here, and source inspection found no evidence warranting that stronger claim.
- A retained-code interpreter/source bootstrap has separate startup trust roots. Byte identity alone is not execution safety or a continuation right. Missing old writer must not force the reader to execute it; existing cross-writer export authority remains separately deferred.

## Proposed bounded comparison

Before deciding omission, commission a fixture-only end-to-end comparison with explicit permission to read the fixture captured assets and, separately, to instantiate a fresh assignment from them. No live audit is necessary to test the byte/source plumbing; actual harness execution would be a later distinct qualification and currently any Claude session launch requires asking the user first.

1. Prepare a known helper asset selection with an external independent byte witness. Inspect a selected non-executable member through a bounded reader after the live original runtime is unavailable. Record that no old code was imported/executed; a hostile source import marker is a useful firing control.
2. Export the full pristine group through an authorized writer-compatible source (or only after separately deciding cross-writer export), relocate it, and remove access to the original session/runtime for the reader. The reader verifies exact manifest/archive/source receipt/collection identities and preserves qualifications. Change selected bytes, remove one group member and substitute a different collection with equal report bytes; each changes only the claim it should. Irrelevant live-state changes are invariance cases.
3. Make the **new mechanism explicit** for turning that group into an independently selected source layout: safe bounded path/type/duplicate validation, hierarchy, modes where relevant, exclusive destination and failure preservation. This could be an explicit export/extraction operation; it must not silently become another mutable audit-owned recovery service. Its ownership, custody promises and disposal responsibility need a named boundary.
4. With separate fresh-assignment authorization, select that source using its own private cache and a fresh audit/lifetime. Verify source identity is the retained version, not current installed code; verify old command/grant/release bindings remain unchanged and cannot authorize the fresh lifetime. This is not a replay promise.
5. Demonstrate the user can accomplish the inspection and source-selection tasks through supported interfaces without private-state repair. Keep unavailable/damaged assets and failed writes explicit; no fallbacks to the live exposed copy or current installation.

Then resolve R1: either decide to omit successor mutable helper recovery and explicitly revise affected preservation/close opportunity clauses, or retain it with a supported preservation route under restricted manager access and a complete lifecycle. Independently inventory actual old recoveries under the finite transition brief. Existing drifted/failed recoveries keep their writer-bound disposition regardless of the new choice. Recovery recapture remains declined unless explicitly reconsidered; the executor's HOME/output facilities are already outside successor scope and do not belong in this choice.
